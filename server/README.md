# 玉屋 管理サーバー

会員・スタッフ・スタンプ・クーポン・お知らせを管理するAPIサーバーです。Node.js、Fastify、SQLiteを使用します。Firebase Authenticationで発行されたIDトークンを検証し、スタッフの権限と付与・使用条件はサーバー側で確認します。

**現在は、本番化に向けたサーバーの土台です。既存のExpo会員アプリはまだこのサーバーへ接続していません。** 実際のFirebaseプロジェクトを使ったログイン、インターネットへの配置、iPhoneからの接続は別途確認が必要です。有料契約・一般公開は実行していません。

まずは、Firebaseの実アカウントやAPIキーなしで開ける、PC内の開発用画面から試せます。

## Windowsで開発用画面を開く

### 1．最新版のファイルを用意する

以前ダウンロードした試作品には、この`server`フォルダーが入っていない場合があります。[最新版のZIP](https://github.com/iichi86/tamayaapp/archive/refs/heads/main.zip)をダウンロードし、展開してください。現在の試作品は保管し、最新版を別のフォルダーへ展開しても使えます。

展開したフォルダーの中に、`server`というフォルダーがあることを確認します。その中には、このREADMEと、サーバー用の`package.json`があります。

Node.jsは**24以上**が必要です。この開発環境では24.19.0を使用しています。以前の会員アプリが動いていても、必要なら次のコマンドでバージョンを確認します。

```bat
node --version
```

`v24...`以降なら、この条件を満たします。

### 2．serverフォルダーで黒い画面を開く

1. Windowsのエクスプローラーで、最新版の`server`フォルダーを開きます。
2. ウィンドウ上部の、フォルダーの場所が表示されているアドレス欄をクリックします。
3. `cmd`と入力してEnterを押します。
4. 黒い画面の入力行が、`...\server>`で終わっていることを確認します。

以前と同じ保存先へ最新版を配置した場合は、黒い画面で次を実行する方法も使えます。

```bat
cd /d "%USERPROFILE%\Downloads\tamayaapp-main\tamayaapp-main\server"
```

保存先が違う場合は、エクスプローラーから開く方法を使ってください。

### 3．必要な部品をインストールする

黒い画面に次を入力して、Enterを押します。

```bat
npm ci
```

処理が終わり、`...\server>`の入力行に戻るまで待ちます。`npm error`が出た場合は、その表示を確認してから次へ進みます。これはサーバー用の部品です。Expoアプリ用の`npm ci`とは別に、初回に実行します。

### 4．開発用サーバーを起動する

```bat
npm run demo
```

黒い画面に、次のような起動先が表示されます。

```text
玉屋 管理サーバー: http://127.0.0.1:3001
```

この画面は動かしたままにします。入力行に戻らず待機しているのが正常です。SQLiteについての`ExperimentalWarning`が表示されても、続いて起動先が表示されていれば起動処理は進んでいます。

### 5．同じPCのブラウザーで開く

ChromeやEdgeのアドレス欄へ、起動後に表示されたアドレスを入力します。標準では次のアドレスです。

```text
http://127.0.0.1:3001
```

これは、**自分のPCでサーバーを起動したあと、そのPCから開くアドレス**です。クラウド環境の公開プレビューではありません。今回は起動用QRを読む操作はありません。

画面に「むさしの玉屋」「開発用・架空データ」が表示されれば、管理サーバーの確認画面を開けています。終了する場合は、黒い画面で`Ctrl + C`を押します。

プロジェクトの一番上のフォルダーで黒い画面を開いている場合は、代わりに`npm run server:setup`、完了後に`npm run server:demo`でも同じ操作ができます。

## 最初に確認する操作

この画面の利用者切り替えは、開発用の確認操作です。本番のFirebaseログインではありません。実在のお客様の情報を入力せず、架空のニックネームを使ってください。

1. 「確認用の利用者」を「店舗管理者」にします。
2. 「体験用の会員」を選び、9スタンプであることを確認します。
3. 「スタンプ付与を確認する」を押し、対象会員を確認して確定します。
4. 残高が0個になり、新しい未使用クーポンが1枚発行されたことを確認します。
5. 利用者を「お客さん：体験用の会員」へ切り替え、同じ結果が表示されることを確認します。
6. 店舗管理者へ戻り、同じ会員の新しいクーポンで「特典利用を確認する」を押して確定します。
7. お客さんへ戻り、使用済みになっていることを確認します。

「お客さん：新規登録を試す」では、ニックネーム登録と0スタンプ開始を確認できます。店舗管理者ではスタッフの停止・再開、店舗スタッフでは付与・特典利用・お知らせ編集を試せます。停止したスタッフの業務操作は、サーバー側で拒否します。

条件はすべて**試作用**です。1会員に日本時間で1日1回、10個で100円引きを1枚発行して10個消費、有効期間は30日です。正式な実店舗の条件は、別途承認して設定する必要があります。

## データの保存と再起動

開発用の保存先は、標準では`server/data/demo.sqlite`です。再起動しても、登録・付与・使用・お知らせの変更は残ります。既存のExpoアプリの端末内データとは別の保存先です。

同じ日に再度サンプルへ付与すると、付与済みとして拒否します。起動のたびに9スタンプへ戻す処理はありません。

最初から試し直す必要がある場合だけ、次の操作を行います。

1. サーバーを`Ctrl + C`で終了します。
2. 保存したいデータがあれば、`server/data`を別の場所へコピーします。
3. `server/data`の中の、`demo.sqlite`で始まる開発用ファイルだけを削除します。`demo.sqlite`本体、存在する場合は`-wal`、`-shm`、`.qr-key`も対象です。
4. `npm run demo`で起動し直します。

**`tamaya.sqlite`など、通常モードのデータは削除しません。** 開発用起動では、通常モードの`DATABASE_PATH`をそのまま流用しない設定にしています。

## 開けない場合

| 表示・状態 | 確認すること |
| --- | --- |
| `npm ci`でファイルが見つからない | 黒い画面が最新版の`server`フォルダーで開いているか確認します。 |
| Node.jsのバージョンで止まる | `node --version`で24以上か確認します。 |
| `EADDRINUSE` | 3001番を別の処理が使っています。別の黒い画面で起動済みの同じサーバーがないか確認します。 |
| `LOCAL_DEMO_ONLY` | 起動先の`127.0.0.1`または`localhost`を、同じPCの通常のブラウザーから開きます。別サイトの埋め込み画面などから操作しません。 |
| 「外部向けアドレス」「production環境」で起動できない | 開発用デモはローカル専用です。`HOST`や`NODE_ENV`を本番向けに設定した環境では起動を拒否します。 |

デモは、PC外へ公開するアドレスで起動できません。スマホからこのデモ画面を開くために、外部公開へ設定を変える手順ではありません。

## Firebase Authenticationへ接続する準備

以下は開発担当向けの接続準備です。**実際のFirebaseプロジェクトの認証情報は、この開発環境には提供されておらず、実アカウントとの通信は未検証です。** 開発用画面から本番Firebaseログインへ切り替わるわけではありません。

### 1．設定ファイルを作る

`server`フォルダーで、次を実行します。

```bat
copy .env.example .env
```

`.env`をエディターで開き、実際に使う値を設定します。`.env`はGitの保存対象から除外しています。

| 設定 | 内容 |
| --- | --- |
| `FIREBASE_PROJECT_ID` | 店舗が使用するFirebaseのプロジェクトID。表示名とは異なります。 |
| `STORE_ID` | 店舗の内部識別子。初期値は`tamaya`。 |
| `STORE_NAME` | 店名。初期値はむさしの玉屋。 |
| `DATABASE_PATH` | 通常モードのDB保存先。初期値は`./data/tamaya.sqlite`。 |
| `QR_SIGNING_SECRET` | 会員提示用QRへ署名する、32文字以上のランダムな秘密値。 |
| `HOST`・`PORT` | 待ち受け先。PC内で確認する初期値は`127.0.0.1`・`3001`。 |
| `CORS_ORIGINS` | 接続を許可するブラウザーの接続元。必要なものだけを指定します。 |

QR用の秘密値は、例えば次で生成し、本人の設定ファイルへ保存します。表示された秘密値をチャットや公開GitHubへ載せません。

```bat
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

### 2．サーバー専用のFirebase認証情報を設定する

Firebase Admin SDKはApplication Default Credentials（ADC）を使用します。Google Cloudの実行環境の権限、またはプロジェクト外に保管した管理用の認証ファイルなどを使って設定します。詳細は[Firebase Admin SDKの公式設定手順](https://firebase.google.com/docs/admin/setup)を確認してください。

ローカルの認証ファイルを使う場合、`.env`の`GOOGLE_APPLICATION_CREDENTIALS`へ、そのファイルの場所を設定します。認証ファイルをスマホアプリや公開リポジトリへ入れません。

サーバーはFirebaseのIDトークンを検証し、失効・無効化されたアカウントも確認します。そのため、サーバーの実行主体には、**対象Firebaseプロジェクトのユーザー情報を確認できる権限**が必要です。複数店舗で別々のFirebaseプロジェクトを使う場合は、それぞれのプロジェクトへの権限を確認します。

`FIREBASE_AUTH_EMULATOR_HOST`が設定された状態では、通常のFirebase認証モードは起動を拒否します。無署名のエミュレータートークンを、本番認証として受け入れる運用にはしません。

### 3．初回の店舗管理者を設定する

先にFirebase Authenticationで管理者本人のアカウントを作り、そのUIDを確認します。そのUIDを使って、サーバー側の管理者を設定します。

```bat
npm run owner -- --uid "Firebaseで確認した管理者本人のUID"
```

引用符内は実際のUIDへ置き換えます。このコマンドは、サーバーを管理できる人が実行する初回設定用です。お客様の登録を、自動的にスタッフや管理者へ昇格させるAPIはありません。

管理者だけがスタッフを追加・停止できます。最後の有効な管理者を、APIから停止・降格する操作は拒否します。

### 4．通常モードで起動する

```bat
npm run build
```

```bat
npm start
```

通常モードでは、役割を自由に切り替えるデモ画面は配信しません。`/health`で`authMode`が`firebase`になることを確認できますが、**起動成功だけでFirebaseの実ログインまで確認できたとは扱いません。** 実際のクライアントからIDトークンを取得して接続を検証します。

## APIの概要

店舗ごとの基本パスは`/api/stores/:storeId`です。例えば玉屋では`:storeId`を`tamaya`に置き換えます。

認証が必要な操作では、Firebaseクライアントで取得した**Firebase IDトークン**を`Authorization: Bearer ...`で送ります。GoogleのOAuthアクセストークンや、利用者が指定した役割の文字列で代用しません。

| メソッド・パス（最初の行以外は基本パス以降） | 操作 |
| --- | --- |
| `GET /api/stores/:storeId` | 店舗・試作用条件を読む（公開）。 |
| `GET /notices` | お知らせを読む（公開）。 |
| `POST /memberships` | 本人の会員登録。本文は`nickname`。0スタンプ開始。 |
| `GET /me` | 本人の会員証・スタンプ履歴・クーポンを読む。 |
| `GET /me/role` | 本人の店舗スタッフ権限を読む。 |
| `GET /me/qr` | 2分間有効の署名付き提示情報を取得する。 |
| `POST /staff/resolve-qr` | スタッフが提示用QRの署名・店舗・期限を確認し、会員を取得する。 |
| `GET /staff/members?query=...` | 会員番号・ニックネームで検索（最大20名）。 |
| `GET /staff/members/:memberId` | スタッフが対象会員を確認する。 |
| `POST /staff/members/:memberId/stamps` | 来店スタンプを付与する。本文は`{}`。 |
| `POST /staff/coupons/:couponId/redeem` | クーポンを使用済みにする。本文は`{}`。 |
| `GET /staff/stats` | 会員数・日本時間の当日付与数・当日利用数を集計する。 |
| `POST /staff/notices`・`PUT /staff/notices/:id` | お知らせの追加・編集。本文は`title`と`body`。 |
| `GET /staff/accounts`・`PUT /staff/accounts/:uid` | 管理者によるスタッフ管理。更新本文は`role`と`active`。 |
| `GET /staff/audit` | 管理者が操作記録を読む。 |

スタッフの変更操作には`Idempotency-Key`ヘッダーが必要です。新しい操作には新しい識別子を付け、通信結果が不明で同じ操作を再送する場合は**同じ識別子と同じ内容**を使います。サーバーは同じ処理を再度実行せず、保存した結果を返します。別の内容で同じ識別子を使った場合は拒否します。停止済みスタッフは、保存済みの結果の再取得も拒否されます。

失敗時の応答形式は`{"error":{"code":"...","message":"日本語の案内"}}`です。例として、未ログインは401、権限不足は403、同日付与・クーポンの使用済み・期限切れなどの競合は409です。

## インターネット上で使う前の残作業

- 既存ExpoアプリへFirebaseログインとAPI接続を実装し、実アカウントと2端末で確認する。
- 本番用の管理画面を用意する。今回の役割切り替え画面はローカル確認専用。
- 正式な店舗条件、退会・アカウント削除、問い合わせ・運用手順を完成させる。
- 公開先、HTTPS、バックアップ、復元、監視、契約・請求の負担者を決めて実装・検証する。

SQLiteは**1台のサーバーと永続ディスク**を使う構成です。複数台へ同じDBファイルをコピーして同時運用したり、再起動でファイルが消える環境へそのまま配置したりする構成にはしません。複数サーバーで運用する段階では、PostgreSQLなどへ保存処理を移す設計を検討します。

バックアップを手動で取る場合は、サーバーを終了してから`data`フォルダー全体を保管します。QR用の秘密値や認証情報は別途、適切に保護して管理します。自動バックアップと復元の運用テストは未実施です。

現在のAPIは、1IPあたり毎分120回の制限を設けています。公開時にリバースプロキシを使う場合は、接続元の扱いやこの制限を実際の構成に合わせて調整します。HTTPS、プロキシ設定、SQLiteの保存場所まで確認してから、インターネット上へ配置します。
