# 本番接続版の引継ぎと、利用者に必要な最小限の作業

更新日：2026年10月31日（日本時間）。Windowsを使う方を想定しています。

この文書は、端末内だけのデモを確認した後、Firebaseでログインし、管理サーバーを通じてSupabaseの共有データベースを使う構成へ進むための案内です。正式な条件は[運用ルール](OPERATING_RULES.md)にまとめています。

**ソースの実装・ローカル検証と、実際の外部サービスへの配置は別です。** Firebaseの`tamayaapp`プロジェクトとWebアプリは作成され、公開設定4項目をアプリの設定例へ反映しました。Firebase Adminの秘密鍵JSONは所有者のPCへ保存されています。Supabaseでは所有者が10テーブルを作成し、全テーブルのRLSが有効と確認しました。2026年10月31日、所有者のWindows PCで公式CAの設定後、専用DBユーザーの作成が完了しました。続けてRenderの公開URL`https://tamayaapp.onrender.com`が提示され、所有者のChromeで`/health`が`status=ok`、`authMode=firebase`と表示されました。サーバー起動とDBの店舗情報取得の確認です。こちらの作業環境からRenderへの通信は制限され、直接の確認はできていません。実Firebaseの会員登録・ログイン、初回オーナー登録、業務操作、本番接続版のiPhone実機確認はこの後です。TestFlight送信やApp Store公開も行っていません。完了した検証と未検証の範囲は[検証結果](VALIDATION.md)を確認してください。

## 何をどこへ保存するか

| 仕組み | 役割 | アプリに秘密情報を入れるか |
| --- | --- | --- |
| Firebase Authentication | メール・パスワードによるログイン、メール確認、パスワード再設定 | Webアプリの公開設定だけを使う |
| 管理サーバー | ログイン情報の検証、スタッフ権限、正式ルール、スタンプ・クーポン計算 | サーバーの公開URLだけを使う |
| SupabaseのPostgreSQL | 会員、残高、履歴、クーポン、お知らせ、権限、操作記録 | DB接続パスワードは入れない |
| Expoアプリ | ホーム・会員証・特典・お店・店舗用画面の表示と操作 | Firebase Admin用秘密鍵、DB接続情報は入れない |

お客様のスマホからSupabaseのテーブルを直接書き換えません。管理サーバーだけが業務データを更新し、毎回、ログイン・権限・店舗・重複を確認します。データベース側でも公開用の利用者にテーブルを開放しません。

共有データは同じ会員アカウントで別端末から利用します。旧デモの端末内データは実会員データとして自動移行しません。本番用のスタンプ・クーポン計算と、旧デモの「10個・100円・30日」を混ぜないためです。

## 利用者が行う最小限のこと

開発側だけでは決められないのは、事業の条件と、サービスの所有者としての本人確認・契約同意です。秘密情報は公開せず、必要な管理アクセスを安全な経路で用意します。作業をまとめると次の順です。

この後の詳細手順を、利用者がすべて手作業で行う必要があるという意味ではありません。所有者のアカウント作成・必要な同意と、安全な管理アクセスを用意した後の接続設定・DB準備・デプロイは、開発担当へ任せられます。現在はそのアクセスがないため、実環境の操作は保留しています。

スタンプ・特典条件と、メール・パスワードによるログインは回答済みです。500円以上の対象商品のお会計で1日1個、5個でスタッフが選ぶ当日の生菓子1つ、有効90日、交換時の追加購入不要、他の割引・クーポンとの併用可を実装へ反映しています。アプリでの商品抽選は行いません。

1. **正しい店舗住所・店舗電話を確認する。** 店舗の資料などで確認します。ワンエイトの電話は、会員サービスの問い合わせ先として別に掲載します。
2. **Firebase・Supabase・サーバー公開先のアカウントを自分の管理下で用意する。** 下の手順で作成します。料金や本人確認への同意は所有者が行います。
3. **秘密情報を公開しない設定欄に登録する。** パスワード・DB接続文字列・Firebase Admin秘密鍵は、チャット、GitHub、アプリの公開設定へ貼り付けません。
4. **最初のオーナーになるアカウントを作り、メール確認を完了する。** そのUIDをサーバーの初回設定で登録します。以後のスタッフ追加・停止はオーナーが店舗用画面で行います。
5. **公開文書と実端末での最終確認を行う。** 運営名義、問い合わせ、実際の委託先・保存地域・保管期間を含むデータの扱いが実態に合っていることを確認し、お客様側と店舗側の別端末で試します。

Appleへの申請に進む時点では、別途Apple Developer Programの本人・事業者登録、契約・料金への同意、Appleが求める確認操作が必要です。手順は[App Store公開手順](APP_STORE.md)にあります。今回はその前の段階です。

## 1．最新版のソースを用意する

以前のZIPには今回の本番接続用ファイルが含まれていない可能性があります。

1. PCのブラウザーで[最新版をダウンロード](https://github.com/iichi86/tamayaapp/archive/refs/heads/main.zip)します。
2. Windowsのエクスプローラーで「ダウンロード」を開きます。
3. ダウンロードした`tamayaapp-main.zip`を右クリックし、「すべて展開」を選びます。
4. 展開先は、以前のフォルダーと区別できる場所にします。以前の`.env`などを不用意に上書きしません。
5. 展開されたフォルダーを開き、`package.json`、`server`、`docs`が見えるところまで進みます。`tamayaapp-main`が二重になっている場合は、内側を開きます。
6. エクスプローラー上部のアドレス欄をクリックし、`cmd`と入力してEnterを押します。そのフォルダーを作業場所にした黒いコマンド画面が開きます。

黒い画面の`C:\…>`より後ろにコマンドを入力します。説明文や先頭の`C:\…>`までコピーしません。コマンドごとにEnterを押し、次の`C:\…>`が戻ったら処理終了です。

Node.jsは24以降を使います。確認は次のコマンドです。

```bat
node --version
```

`v24…`以降と表示されることを確認します。ソースの導入・起動コマンドは[README](../README.md)と[サーバーのREADME](../server/README.md)にまとめています。`npm run demo`は以前のSQLite開発デモであり、Supabase接続版の運用開始ではありません。

## 2．Firebaseでログインを準備する

Firebaseは、今回はログインだけに使います。Firestore、Firebase Storage、Cloud Functionsの契約・有効化は、この構成の必須作業ではありません。

ログイン後も、管理サーバーはFirebaseのIDトークンと失効状態を確認します。認証をログイン画面だけで終えて、その後のAPIを無認証にする意味ではありません。スタンプなどの業務データはFirebaseへ保存しません。

1. [Firebaseコンソール](https://console.firebase.google.com/)を開き、事業で管理するGoogleアカウントでログインします。
2. 「プロジェクトを追加」から、玉屋用のプロジェクトを作ります。Google Analyticsを使うか聞かれた場合、今回の機能に必須ではありません。
3. プロジェクトのメニューから`Authentication`を開きます。
4. 初回の開始操作を行い、ログイン方法の`メール/パスワード`を有効にします。メールリンクだけの方式やSMSを選ぶ手順ではありません。
5. プロジェクトの設定から、Webアプリの登録（`</>`のアイコン）を行います。ExpoのFirebase JavaScript SDKで使う公開設定を取得するためです。Firebase Hostingの有効化は必須ではありません。
6. 表示される設定の`apiKey`、`authDomain`、`projectId`、`appId`を確認します。これらは公開アプリの接続設定です。サービスアカウントの秘密鍵とは別物です。
7. Authenticationのメールテンプレートで、確認メール・パスワード再設定メールの表示名や送信内容を確認します。一般のお客様へ送る前に、自分のメールで到着とリンクの動作を確かめます。
8. ブラウザー公開版を使う場合は、実際の公開ドメインをAuthenticationの承認済みドメインへ追加します。設定画面の名称は変更される場合があります。

2026年10月30日時点で、上記のWebアプリ登録と公開設定4項目の受け渡しは完了しています。最新版の直下`.env.example`には受け取った設定が入力済みです。管理APIのURLはまだ決まっていないため空欄のままです。この段階では実サービスへログインできたとは扱いません。

サーバーには、IDトークンを検証し、退会時に対象ユーザーを削除できる管理用の認証が必要です。Google Cloud上の実行用サービスアカウントを使うか、サーバー公開先の秘密ファイルとしてサービスアカウントJSONを登録します。JSONはGitHubに置かず、アプリにも含めません。サーバーだけに必要な権限を与えます。

Renderで秘密ファイルを使う場合は、Firebaseのプロジェクト設定から「サービスアカウント」内のFirebase Admin SDK用設定を開き、管理者が秘密鍵JSONを生成します。画面が変わっている場合は、Google Cloud側でサービスアカウントと必要な認証権限を確認します。

ダウンロードしたJSONは、例えば`C:\tamaya-private\firebase-admin.json`のように、展開したプロジェクトの外側へ保管します。PCでサーバーを設定するときは、`server/.env.production`の`GOOGLE_APPLICATION_CREDENTIALS`へ`C:/tamaya-private/firebase-admin.json`のような実際のパスを入れます。RenderではSecret Filesにファイル名`firebase-admin.json`で登録し、`GOOGLE_APPLICATION_CREDENTIALS=/etc/secrets/firebase-admin.json`を使います。JSONの内容は秘密ファイルの設定欄にだけ入れ、チャットやGitHubへ貼り付けません。

FirebaseのWeb用`apiKey`を秘密鍵の代わりにサーバーへ渡しても、管理用認証はできません。管理用JSONを`EXPO_PUBLIC_…`へ設定することも禁止です。無料枠・メール送信制限・サービスの料金は、契約時の管理画面で確認します。

## 3．Supabaseに共有データベースを作る

1. [Supabaseの管理画面](https://supabase.com/dashboard)を開き、所有するアカウントでログインします。
2. Organizationを作成または選択します。料金・管理名義を確認してください。
3. `New project`を押し、玉屋用のプロジェクトを作ります。検証用と本番用は、名前と接続先で区別します。
4. データベースのパスワードを作成し、パスワード管理アプリなどに保存します。
5. RegionはTokyoが選べる場合は候補にし、提供中の地域とデータの保存場所を確認して選びます。
6. プロジェクトの準備が終わったら、`Connect`などの接続案内を開きます。
7. 管理サーバーから使えるPostgreSQLの接続文字列を確認します。直接接続、または公開先のネットワーク条件に合うプーラーを使います。プーラーの場合は案内されるユーザー名・ホスト・ポートをそのまま使います。
8. `postgres.〜`という所有者の接続情報は、PCの**`DATABASE_MIGRATION_URL`**で初期準備にだけ使います。公開APIの`DATABASE_URL`には、後の`db:provision`で生成する権限を絞った専用ユーザーの接続情報を使います。所有者の接続情報を公開APIへ常設しません。

2026年10月30日に確認した接続先は次のとおりです。これはパスワードを含まない公開情報で、これだけではDBに接続できません。

| 項目 | 今回の値 |
| --- | --- |
| 接続方法 | Session pooler |
| host | `aws-0-ap-northeast-2.pooler.supabase.com` |
| port | `5432` |
| database | `postgres` |
| 初期準備用user | `postgres.ohpbgirqcfxinhntmavk` |
| DBの地域 | 韓国・ソウル（`ap-northeast-2`） |

`Connect`の実際の画面では、上部の`Direct`タブ内にある`Connection Method`で`Session pooler`を選び、`Type`を`URI`にします。`Source`という項目を探す必要はありません。下部の`Connection parameters`に4項目が表示されます。

SQL Editorでは同梱SQLの実行後、所有者から10テーブルすべて`rowsecurity=true`との報告・画面を受けています。専用ログインの権限と、アプリからの実接続の確認はこの後です。

この構成では、Supabaseの公開用キーや`service_role`キーをExpoアプリへ設定して、会員テーブルへ直接接続する必要はありません。Supabaseの認証メールやカスタムSMTPの設定も、Firebaseでのログインには使いません。

サーバーとリモートDBの接続はTLSの証明書検証を有効にします。接続エラーを直すために`rejectUnauthorized: false`を設定しません。提供元のCA指定が必要な場合は、サーバー側のCA設定を使います。トランザクション方式のプーラーを使う際、実装は接続をまたいで準備済みクエリ名を保持しない形で利用します。

DBのテーブルは、同梱のマイグレーションで作成します。会員データのスキーマは公開利用者に開かず、RLSと権限を設定します。管理画面で「動かないから全テーブルを公開する」という変更はしません。SQLと実行コマンドは[サーバーのREADME](../server/README.md)に従います。

本番では、休止条件・バックアップ・復旧・接続数を含めてプランを選びます。特定の無料枠で永続的に無条件運用できるという保証はありません。

開発担当がPCからDBを準備する場合は、`server`フォルダーを開き、そのエクスプローラーのアドレス欄から`cmd`を開きます。黒い画面の現在地が`…\server>`であることを確認し、次を1行ずつ実行します。

```bat
npm ci
if not exist .env.production copy .env.production.example .env.production
notepad .env.production
```

このファイルは**サーバー用の秘密設定**です。プロジェクト直下のアプリ用`.env`と区別します。今回の`DATABASE_MIGRATION_URL`は、受け取ったホスト・ポート・DB名・所有者ユーザーを入力済みで、パスワード部分を`[YOUR-PASSWORD]`としてあります。**この文字はそのまま残せます。** DB準備コマンドは実行時に、PCの黒い画面でパスワードを非表示入力するよう求めます。入力中に文字が表示されないのは正常です。DB作成時のパスワードを入力してEnterを押します。入力した所有者パスワードは設定ファイルへ書き戻しません。

DBの初期準備だけなら、APIの公開URL、QR署名用秘密値、Firebase管理用JSONはまだ不要です。`DATABASE_URL`は、後の手順で専用ユーザーの接続情報を生成してから入れます。SQL Editorでテーブル作成を完了した今回のケースでは、次のマイグレーションを繰り返す必要はなく、その次の`db:provision`へ進めます。テーブル未作成の場合は、まず次を実行します。

```bat
npm run db:migrate
```

`PostgreSQLの会員サービス用テーブルを準備しました。`と表示されたら、スキーマの準備が終わっています。SQL Editorで既に準備済みの場合も、次の専用ユーザー作成は必要です。同じ黒い画面で次を実行します。

```bat
npm run db:provision
```

このコマンドは`tamaya_runtime`という実行専用ログインとランダムなパスワードを作り、サーバー用の`tamaya_api`権限だけを付けます。DB管理者やRLSを回避する権限は持たせません。接続情報は画面へ表示せず、**`server/.env.runtime.generated`**という秘密ファイルに保存します。Supabaseの共有プーラーを使う場合のユーザー名の接尾部分も引き継ぎます。

成功メッセージが出たら、次を実行します。

```bat
notepad .env.runtime.generated
```

メモ帳にある`DATABASE_URL=…`の行を、`server/.env.production`の同名の行へコピーして保存します。PC内の`.env.production`へは、行全体をそのままコピーできます。公開先の秘密設定へ入れるときは、値である接続URLだけを入れ、先頭の`DATABASE_URL=`と両端の引用符は含めません。

**生成ファイル・接続URLは、チャット、GitHub、アプリ側の`.env`、画面のスクリーンショットで共有しません。** 公開先には実行用の`DATABASE_URL`だけを登録し、管理者用の`DATABASE_MIGRATION_URL`を常設しません。PCの管理用設定もアクセスできる人を制限して保管します。

この初回設定は、既存の生成ファイルを上書きせず、既存の`tamaya_runtime`のパスワードも勝手に変更しません。「すでに存在する」エラーが出た場合は、元の秘密設定が残っているか開発担当が確認します。生成ファイルやDBロールを削除して繰り返す手順にはしません。DBの詳しい権限は[DB設定の説明](../server/supabase/README.md)を参照してください。

### DB準備が失敗した場合

2026年10月31日以降の版は、パスワード・接続URL・DBからの生のエラー文を表示せず、`[DB_AUTH_FAILED]`などの固定コードと案内を表示します。コード部分だけを開発担当へ伝えます。

| 表示コード | 次の確認 |
| --- | --- |
| `DB_AUTH_FAILED` | SupabaseのDatabase passwordと所有者ユーザー名。Supabaseへのログイン用パスワードとは別 |
| `DB_TLS_CERTIFICATE` | 提供元のCA証明書と`DATABASE_CA_PATH`。TLS検証を無効にして回避しない |
| `DB_DNS_FAILED` / `DB_NETWORK_FAILED` | 接続先、ネットワーク制限、Supabaseの稼働状態 |
| `DB_PERMISSION_DENIED` / `DB_SCHEMA_NOT_READY` | 所有者の接続先と、初期SQLの適用状況 |
| `DB_OUTPUT_EXISTS` / `DB_RUNTIME_ROLE_EXISTS` | 既存設定を保管したまま担当へ報告。ファイルやロールを消して繰り返さない |
| `DB_OUTPUT_PERMISSION` / `DB_OUTPUT_WRITE_FAILED` / `DB_CLEANUP_FAILED` | PC内の保存先、権限、空き容量。生成ファイルの中身を共有しない |
| `DB_COMMIT_UNCERTAIN` | DBの確定応答が不明。生成された接続設定は保持されるため、そのまま保管して担当へ報告 |

古い版の「DB実行用設定を生成できませんでした」という表示だけでは原因を判定できません。担当が案内する修正版の`src/production/setupErrors.ts`と`src/production/provision.ts`だけを現在の`server`フォルダーへ取得すれば、同じPC内の設定を使って再実行できます。依存ライブラリの変更はありません。更新のダウンロードに失敗した場合は、その時点で止めて表示を伝えます。

2026年10月31日、所有者のWindows PCで`DB_TLS_CERTIFICATE`と表示されることを確認しました。これはTLS証明書の検証に失敗したことを示し、入力したDBパスワードの正誤はまだ判断できません。Supabaseの公式[管理画面の設定](https://github.com/supabase/supabase/blob/master/apps/studio/hooks/custom-content/custom-content.json)と[SSL画面の実装](https://github.com/supabase/supabase/blob/master/apps/studio/components/interfaces/Settings/Database/SSLConfiguration.tsx)で、本番用CAの取得先を確認しました。同じ`server`フォルダーのコマンド画面で、次を1行ずつ実行します。

```bat
curl.exe -fLsS "https://supabase-downloads.s3-ap-southeast-1.amazonaws.com/prod/ssl/prod-ca-2021.crt" -o "supabase-ca.crt"
set "DATABASE_CA_PATH=supabase-ca.crt"
npm run db:provision
```

最初のダウンロードで`curl:`から始まるエラーが出た場合は、次のコマンドへ進みません。ブラウザーから取得する場合は、[対象プロジェクトのDatabase Settings](https://supabase.com/dashboard/project/ohpbgirqcfxinhntmavk/database/settings)の`SSL configuration`にある`Download certificate`を使います。証明書を取得しただけでは適用されず、アプリ側の`DATABASE_CA_PATH`設定が必要です。

この`set`は現在のコマンド画面だけに有効です。接続成功後は、PC内の`server/.env.production`の`DATABASE_CA_PATH=`を`DATABASE_CA_PATH=supabase-ca.crt`へ変更して保存します。公開先でも証明書ファイルをサーバー側へ配置し、その実際のパスを`DATABASE_CA_PATH`に設定します。証明書は公開情報で、Firebase Adminの秘密鍵とは異なります。TLSの接続先名と証明書の検証は有効のままです。

クラウド作業環境ではCA配布先への取得が403となり、証明書本体の内容・有効期間・所有者環境での接続成功はまだ確認できていません。公式URLの出典確認と、実接続の成功は区別します。

専用ユーザーの作成はDBトランザクション内で行います。接続・権限エラーなどで確定前に失敗した場合はロールバックし、今回作成した途中ファイルのみを除去します。接続設定は書き込み・同期・ファイルを閉じる処理を終えてからDBを確定します。確定要求の応答が失われた場合は、作成されたかもしれない専用ユーザーの接続情報を失わないよう、生成ファイルを残します。

## 4．管理サーバーを公開先へ置く

公開先はRenderです。ソースにはDockerとデプロイ用設定を用意し、Node.js APIをHTTPSで動かす構成を使います。初期検証用の設定はFreeです。2026年10月31日、所有者の操作で公開URLが作成され、`/health`の成功報告を受けました。実店舗運用前に休止・起動時間・常時稼働の条件を確認し、必要な有料契約は所有者が別途選びます。

1. サーバー公開先の自分のアカウントへログインします。
2. GitHubの`iichi86/tamayaapp`を参照できるよう、必要なリポジトリだけの連携を許可します。
3. 同梱のデプロイ設定を読み込み、対象ブランチと実行内容を確認します。
4. 料金、休止・起動時間、保存・ログの条件を確認し、プランを選びます。
5. サーバー用の環境変数を登録します。秘密値はSecret／Environment等の非公開設定欄へ入れます。
6. 最初の起動前に、店舗設定の内容とマイグレーションを確認します。
7. Renderでは標準の`RENDER_EXTERNAL_URL`から公開URLを読み取ります。独自ドメインや別の公開先を使う場合は、`PUBLIC_BASE_URL`にそのHTTPSオリジンを設定します。
8. ブラウザー版も公開する場合は、`CORS_ORIGINS`へそのHTTPSのオリジンだけを設定します。iPhoneのネイティブ通信はCORSによる許可を使いません。
9. デプロイ結果で起動成功を確認し、公開URLの`/health`を開きます。DB接続や認証に必要な設定が不足していたら、本番として運用を開始しません。

サーバーが使う主な設定は次のとおりです。最終的な記入例はサーバー側の設定例とREADMEを参照してください。

### 今回のWindows PCからRenderへ登録する

2026年10月31日、所有者から新規Web Service画面の`Advanced`内に`Secret Files`が表示されているとの回答を受けました。対象は`iichi86/tamayaapp`、Languageは`Docker`、Branchは`main`、Root Directoryは空欄、Dockerfile Pathは`server/Dockerfile`、Docker build contextはリポジトリーのルート、初期確認用Computeは`$0/month`です。無料であることを画面の金額表示でも確認します。

設定値の手入力を減らすため、最新版の`server/src/production/prepareRender.ts`を用意しました。現在の`server`フォルダーで次を実行します。古いZIPの場合は、このファイル1つだけを担当から案内された公式リポジトリーのURLから取得できます。


この処理は、実行専用DBの生成ファイルと、今回保存した`supabase-ca.crt`を読み取って確認します。管理者のDB接続情報や未設定の値、期限外・不正なCAは受け付けません。QR署名用の秘密値をランダムに生成し、必要な9項目をローカルの`.env.render.generated`へ保存します。ファイルの中身は画面に表示せず、外部通信もしません。元のDB設定・CA・既存のRender設定ファイルは上書きしません。

1. Renderの作成画面で`Environment Variables`の`Add from .env`を開きます。ファイルを選ぶ画面なら、現在の`server/.env.render.generated`を選びます。テキストを貼る画面なら、PCで`notepad .env.render.generated`を実行し、中身全体をRenderの入力欄にだけコピーします。取り込みの確定ボタンを押して、9項目が追加されたことを確認します。入力済みの画面や値をチャットへ送る必要はありません。

3. 同じ場所に、名前を`firebase-admin.json`として、以前Firebaseからダウンロードした管理用JSONを登録します。ファイル選択形式なら元のJSONを選び、内容入力形式ならメモ帳から全文をその入力欄だけへコピーします。保存名の欄は`firebase-admin.json`にそろえます。内容をチャットやGitHubへ貼りません。

生成される`DATABASE_URL`には、今回の専用ログインだけを使います。`GOOGLE_APPLICATION_CREDENTIALS`は`/etc/secrets/firebase-admin.json`、`DATABASE_CA_PATH`は`/etc/secrets/supabase-ca.crt`です。`PUBLIC_BASE_URL`はRenderが提供する`RENDER_EXTERNAL_URL`から取得するため、作成前にURLを推測して入力しません。初期確認用のネイティブiPhone接続に`CORS_ORIGINS`の設定は不要です。

| 設定 | 用途 |
| --- | --- |
| `APP_ENV=production` | 本番として起動 |
| `AUTH_MODE=firebase` | 実Firebaseを使う。エミュレーターは本番不可 |
| `DATABASE_URL` | Supabase PostgreSQLの秘密の接続文字列 |
| `FIREBASE_PROJECT_ID` | 本人確認に使うプロジェクトID |

## 5．最初のオーナーとスタッフを登録する

1. オーナー本人がアプリでアカウントを作り、メール確認を済ませます。
2. アプリの「アカウント」で、その人の「ログインID（スタッフ権限の登録用）」を確認します。これがUIDです。初回設定をする担当者は、FirebaseのAuthenticationのユーザー一覧でもメールアドレスと照合できます。UIDはパスワードではありません。
3. サーバー管理者が、同梱の初回オーナー設定コマンドへそのUIDを指定します。正しいDB・店舗を対象にしていることを確認してから実行します。
4. オーナーがアプリへ再ログインまたは情報を再読み込みし、店舗用メニューを開けることを確認します。
5. スタッフもそれぞれアカウント作成・メール確認を行い、ニックネームの会員登録まで完了します。
6. スタッフが自分のアカウント画面のログインIDをオーナーへ伝えます。オーナーが店舗用画面でそのUIDと役割を指定し、追加します。普段のスタッフ追加のためにFirebaseの管理者パスワードを渡す必要はありません。
7. そのスタッフの端末で業務画面が開けることと、停止後に業務操作が拒否されることを確認します。

普段のオーナー操作に、DBパスワードやFirebase Admin秘密鍵は使いません。スタッフへそれらを配布する必要もありません。最後のオーナーを止める操作は拒否されます。別オーナーを追加してから交代してください。

サーバー管理者がPCのソースから初回設定を行うコマンドは、`server`を現在地にして次のとおりです。引用符の中を、確認した本人のUIDに置き換えます。

```bat
set "DATABASE_CA_PATH=supabase-ca.crt"
npm run owner:production -- --uid "ここを本人のUIDに置き換える" --credentials "管理用JSONの実際のパス"
```

これは旧デモ・SQLite用の`npm run owner`とは別のコマンドです。2026年10月31日の修正版は、初期準備用`DATABASE_MIGRATION_URL`を使い、DBパスワードを非表示入力します。PCの`server/.env.production`にある管理用接続先をそのまま使え、HTTPの公開URLやQR秘密値は不要です。`--credentials`には、そのPCに保存したFirebase管理用JSONのファイルパスを指定します。エクスプローラーでJSONを右クリックし「パスのコピー」を使えば、内容を共有せずに指定できます。`GOOGLE_APPLICATION_CREDENTIALS`に正しいローカルパスを設定済みなら、この引数は省略できます。古いZIPの場合は`src/production/owner.ts`だけを担当が案内する修正版へ更新してください。

管理用JSONのプロジェクト、Firebaseの対象ユーザー、既存DBの店舗のプロジェクトが一致し、本人のメール確認が済み、停止されていないことを確認してから権限を設定します。共有DBの店舗情報や公開URLをPC内の設定で上書きしません。UIDや管理用JSONの中身をログへ出さず、エラーは`OWNER_…`または既存の`DB_…`コードで確認できます。

Dockerの実行用イメージでは開発用の`tsx`を含めないため、同じ処理はコンパイル済みの`node dist/server/src/production/owner.js --uid "本人のUID" --credentials "管理用JSONのパス"`で実行します。Renderの無料プランのShellを前提にせず、今回の初回設定は所有者のPCから行えます。

## 6．アプリを本番接続先へ向ける

Expo側に設定するのは、管理サーバーのURL、店舗ID、Firebase Webアプリの公開設定です。`EXPO_PUBLIC_…`という名前の設定はアプリへ埋め込まれるため、誰でも取得し得るものとして扱います。

`package.json`が見えるプロジェクト直下で、エクスプローラーのアドレス欄から`cmd`を開き、次を1行ずつ実行します。

```bat
npm ci
if not exist .env copy .env.example .env
notepad .env
```

すでに`.env`がある場合は、コピー時に上書きする前に内容を保存してください。メモ帳が開いたら、次を実際の値へ置き換え、Ctrl＋Sで保存します。

| アプリ用設定 | 入れる値 |
| --- | --- |
| `EXPO_PUBLIC_APP_MODE` | `production` |
| `EXPO_PUBLIC_API_URL` | 稼働している管理サーバーのHTTPS公開URL |
| `EXPO_PUBLIC_STORE_ID` | `tamaya` |
| `EXPO_PUBLIC_FIREBASE_API_KEY` | 登録したFirebase Webアプリの`apiKey` |
| `EXPO_PUBLIC_FIREBASE_AUTH_DOMAIN` | 同じWebアプリの`authDomain` |
| `EXPO_PUBLIC_FIREBASE_PROJECT_ID` | 同じWebアプリの`projectId`。管理サーバーと一致させる |
| `EXPO_PUBLIC_FIREBASE_APP_ID` | 同じWebアプリの`appId` |

今回の公開URLは`https://tamayaapp.onrender.com`です。最新版の`.env.example`へ反映しています。すでにPCへ展開した版は古い設定例のままなので、アプリ直下の`.env`にある行を`EXPO_PUBLIC_API_URL=https://tamayaapp.onrender.com`へ変更します。現在地が`…\server>`なら`cd ..`でアプリ直下へ移動できます。この展開先でアプリ側の依存をまだ導入していない場合は、上記の`npm ci`を実行します。サーバー側で済ませた`npm ci`とはインストール先が異なります。

保存したらメモ帳を閉じ、黒い画面で次を実行します。

```bat
npm start -- --go --clear
```

起動後のQRをiPhoneの標準カメラで読み取り、Expo Goで開きます。黒い画面は開いたままにしてください。起動用QRの詳しい場所と操作は[iPhone手順](IPHONE.md)を参照してください。今回追加したFirebase JavaScript SDKはExpo Goで使う構成で、React Native Firebaseのネイティブライブラリを追加する手順ではありません。Expo GoとプロジェクトのSDKが一致することは、その時点の端末表示でも確認します。

PCブラウザーで画面を開く操作は、起動中の黒い画面で`w`です。ただし実Render APIへブラウザーから接続するには、そのブラウザーの接続元をサーバーの`CORS_ORIGINS`へ登録する必要があります。今回のネイティブiPhone用設定ではブラウザーのAPI通信を許可していないため、まずiPhoneのExpo Goで確認します。アプリを停止する場合はCtrl＋Cです。

### 初回の本人登録とログイン確認

1. iPhoneで「ホーム」の`会員登録・ログイン`、または下部の`会員証`を開きます。
2. `はじめての方：会員登録`を押し、自分で受信できるメールと12文字以上のパスワードを入力します。規約・プライバシーの同意を確認して`確認メールを送って登録する`を押します。
3. 受信した確認メールのリンクを開き、Expo Goへ戻って`メール確認後、会員登録へ進む`を押します。メール未着時は`確認メールを再送する`があります。
4. 20文字以内のニックネームを入力し、表示内容と同意を確認して`会員登録して会員証を表示`を押します。通常の本人登録は0スタンプで開始します。
5. 右上の`設定`を開き、`ログインID（スタッフ権限の登録用）`を確認します。これが初回オーナー設定コマンドのUIDです。パスワードやDB接続情報とは異なります。
6. オーナー設定後は`設定`から`最新の情報に更新`を押し、もう一度設定を開いて`店舗スタッフの画面へ`を確認します。

これらは実Firebaseの登録・確認メール・管理APIの本人登録を検証する操作です。`/health`の成功だけで、ここまで成功したとは扱いません。

署名済みの配布アプリを作る前に、`EXPO_IOS_BUNDLE_IDENTIFIER`へ所有者が使える一意のIDを設定します。`RELEASE_BUSINESS_APPROVED`は公開文書・正式特典・運用の内容を確認した後にだけ承認済みへ変更します。設定の不足確認は次のコマンドです。

```bat
npm run production:check
```

この確認は、公開URLへの実際の疎通、実iPhoneの操作、Apple審査への合格を代行するものではありません。

外部サーバーがまだない段階ではローカルのDB・認証エミュレーターで開発確認できますが、これは本番へのログイン成功とは別です。設定不足時に旧デモへ自動で切り替えて、接続できたように表示する設計にはしません。

PCブラウザーの`127.0.0.1`はそのPC自身です。iPhoneで同じURLを指定するとiPhone自身を指すため、PCのサーバーには接続できません。本番確認では、iPhoneから到達できる実際のHTTPS公開URLを使います。ローカルの認証エミュレーターをインターネット公開する方法で代用しません。

### 開発担当向け：実サービスに接続せず連携を確認する場合

この節は任意です。利用者がDockerやJavaを準備しなければ、本番アプリを使えないという意味ではありません。

Node.js 24以降、動作中のDocker、Firebase CLIの実行に必要なJavaがある開発環境では、プロジェクト直下から次を実行できます。

```bat
npm ci
npm --prefix server ci
npm --prefix tools ci
node scripts/local-services.mjs
```

この起動スクリプトは、検証用PostgreSQLコンテナ、Firebase Authenticationエミュレーター、本番用APIのローカル構成、Expoのブラウザープレビューを順番に起動します。準備完了の`TAMAYA_LOCAL_READY`が表示されたら、同じPCで`http://localhost:8083`を開きます。終了は起動した黒い画面でCtrl＋Cです。

実際のFirebase・Supabaseには接続せず、架空の特典だけで動きます。検証用DBは終了時に削除されます。実際のお客様向けのサービスを公開する手順ではありません。実メールの配信、公開先のHTTPS、実Supabaseの権限・TLS、iPhoneのカメラ・実機挙動は、このローカル環境だけでは検証できません。

## 7．TestFlightの前に最後の確認をする

本番データを使う前に、検証用の会員アカウントで行います。端末は、お客様側と店舗側で別々にします。

| 確認する操作 | 合格の目印 |
| --- | --- |
| 新規登録・確認メール・会員登録 | メール確認後、0個の会員証が作られる |
| 別端末で同じアカウントへログイン | 同じ会員番号・残高・履歴になる |
| スタッフ付与 | 対象会員と会計金額を確認してから成立し、お客様側に反映される。499円は拒否、500円は条件を満たす |
| 5個での発行 | 4個からの1回の付与で残高0、生菓子1つのクーポンが1枚増える |
| 同日・連打・同時付与 | 履歴・残高・クーポンが重複しない |
| 使用・再使用 | 追加購入なしでスタッフ確認後に使用済みになり、2回目は拒否される |
| 特典の案内 | スタッフが当日の生菓子から選ぶこと、他の割引・クーポンと併用できることが分かる。ギフト商品の無料引換とは表示しない |
| 期限 | 発行から90日の期限を過ぎたクーポンは使えない |
| 権限 | お客様から付与不可、停止スタッフは業務不可、他人の会員情報を取得不可 |
| お知らせ・店舗情報 | サーバーで設定した内容がホーム・お店に反映される |
| オフライン | 誤って付与成功と表示しない。復帰後の再試行で重複しない |
| 再起動 | アプリとサーバーを再起動してもDBの情報が維持される |
| 機種変更・再設定 | 同じメールで復旧でき、パスワード再設定メールが届く |
| 退会 | 確認後に退会でき、削除保留時は未完了であることが分かる |
| 文字・カメラ | 実iPhoneの文字拡大・小画面・セーフエリア・カメラ権限で主要操作ができる |
| 公開文書 | HTTPSの利用規約・プライバシー・問い合わせページが実際に開く |
| 障害復旧 | 監視通知と、検証用DBへのバックアップ復元を確認できる |

スタンプ付与時の会計金額はスタッフが入力してサーバーが条件を判定し、記録へ残します。レジ・POSとは連携していないため、対象商品であることと実際の会計との一致は店頭で確認します。500円以上の条件は付与時だけで、特典交換に追加購入は不要です。

4個・期限切れなどの境界条件は自動テスト用データで確認できます。実際のお客様の残高を直接書き換えたり、本番DBへ開発サンプルを入れたりする手順にはしません。

ブラウザーの確認結果をiPhone実機の確認済みとして記録しません。iOS向けJavaScriptのexport成功も、署名済みアプリやTestFlightでの動作確認とは別です。

上の確認が終わったら、[App Store公開手順](APP_STORE.md)のEAS・Apple登録・ビルドへ進みます。アプリの名前・Bundle ID・アイコン・公開文書・実稼働URL・審査用アカウントを、実際の所有者とサービス内容に合わせて確定してください。


## 開発側で追って完了すること

所有者がサービスのアカウントを作成し、管理アクセス・秘密設定を用意できた後は、DBへの適用、実Firebaseとの疎通、常設サーバーの起動、初回オーナー設定、バックアップ復元・監視の確認、公開文書の実環境との照合を開発担当で進められます。これらが終わるまでは実店舗の会員運用を開始しません。

現在の依存監査では、アプリの開発CLI等に未解消のhigh報告が残ります。サーバー実行用の報告は0件です。影響と残作業は[検証結果](VALIDATION.md#依存ライブラリの監査)を確認してください。
