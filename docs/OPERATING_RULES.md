## 正式なスタンプ・特典の条件

| 項目 | 条件 |
| --- | --- |
| スタンプ | 500円以上のお会計がある来店1回につき1個 |
| 同じ会員への付与上限 | 日本時間で1日1回 |
| クーポン発行 | 5個に到達した時に5個を消費し、1枚発行 |
| クーポンの有効期間 | 発行日時から90日 |
| スタンプ対象の商品 | 生菓子・ギフト商品 |
| 5個で受け取れる特典 | ランダムで生菓子を1つ |
| 生菓子を選ぶ方法 | 当日の対象商品からスタッフが選んで渡す。アプリで抽選しない |
| クーポン交換時の購入条件 | 追加購入は不要。500円以上の条件はスタンプ付与時だけ |
| 他の割引・他のクーポンとの併用条件 | 併用できる |
| 新規会員の開始残高 | 0個 |
| 使用済み・期限切れのクーポン | 再利用できない |

旧デモの「10個・100円引き・30日」は正式条件に引き継ぎません。今回の特典は、5個で受け取る生菓子1つです。

ギフト商品はスタンプ対象です。特典で交換する商品は生菓子1つであり、ギフト商品を無料で渡す条件にはしません。スタッフが当日の生菓子から選ぶため、アプリで抽選したり、特定の商品を保証したりする仕組みは設けません。

正式条件は店舗設定へ反映済みです。実際のお客様向けに開始するには、Firebase・共有DB・公開サーバーへの接続、店舗情報と公開文書の確認、実端末での最終確認が必要です。設定の`operationsEnabled: true`は、これらの準備や公開が終わったことを意味しません。

有効期限はサーバーの発行時刻を基準に計算し、期限の時刻に達したら使用不可とします。「90日目の閉店まで」など、別の締め方にする場合は開始前に条件と実装を変更します。

## お客様の登録・ログインと機種変更

利用者の回答に基づき、Firebase Authenticationの**メールアドレスとパスワード**を使います。メールの本人確認を完了してから、会員登録・会員機能を利用します。ニックネームは画面表示用です。

1. メールアドレスとパスワードでアカウントを作成します。
2. 届いた確認メールのリンクを開きます。
3. アプリに戻り、確認完了を反映します。
4. 利用規約・プライバシーの内容を確認し、ニックネームを登録します。
5. 0個の会員証が作成されます。

Firebaseは本人確認を担当し、会員情報・スタンプ・クーポン・スタッフ権限は管理サーバーと共有データベースで扱います。Supabase AuthenticationやFirestoreへ会員データを重複保存する構成ではありません。

「ログインだけに使う」は、認証以外の業務データをFirebaseへ保存しないという意味です。安全に操作するため、ログイン後も認証トークンの更新と、サーバー側での本人・失効の検証は行います。

機種変更後は、**以前と同じメールアドレスのアカウントにログイン**すると、サーバーにある同じ会員情報を開きます。パスワードを忘れた場合は、登録メール宛の再設定を使います。

「店舗側端末での接続」というご希望は、店舗で会員を確認してログイン・再設定を案内する運用として扱います。スタッフがニックネームだけを根拠にログインを代行したり、別アカウントへ残高を移したりする機能は設けません。登録メールも使えない場合の本人確認・移行手続きは、別途決める必要があります。

## 店舗スタッフとオーナー

| 役割 | 操作 |
| --- | --- |
| お客様 | 自分の会員証・履歴・クーポンの確認、店頭提示、ニックネーム変更、退会 |
| スタッフ | 会員の確認、来店スタンプ付与、対象クーポンの使用、店舗のお知らせ編集、集計の確認 |
| オーナー | スタッフの業務操作に加え、スタッフの追加・停止、権限の管理、操作記録の確認 |

店頭では、その場にいる登録済みスタッフが操作できます。各スタッフは自分のログインを使い、オーナーがそのアカウントへ権限を付与します。勤務しているという理由だけで、お客様用アカウントを自動でスタッフ扱いにはしません。

スタッフ追加・停止の管理者はオーナーです。停止した権限は次のサーバーへの要求から拒否されます。お客様は自分でスタッフ権限を付けられません。最後の有効なオーナーを停止・削除して、管理できる人がいなくなる操作は拒否します。

最初のオーナーだけは、サーバーを管理する担当者が設定用のコマンドで登録します。アプリの画面から誰でも最初のオーナーになれる仕組みにはしません。

## 店頭での受付

1. お客様がアプリの「会員証」を開きます。
2. スタッフが自分のアカウントで店舗用画面を開きます。
3. 会員証のQRを読み取り、表示された会員を確認します。
4. 来店スタンプなら、お会計を確認して金額を入力します。500円以上であること、対象会員、当日まだ付与していないことを確認してから確定します。
5. クーポンなら、お客様の提示と対象商品・期限を確認し、使用を確定します。追加購入を求めず、スタッフが選んだ当日の生菓子1つを渡します。他の割引・クーポンとの併用もできます。

スタンプ付与時に入力した会計金額はサーバーで条件を判定し、記録に残します。499円以下では付与できません。レジやPOSとは接続していないため、対象商品のお会計であることと、入力が実際の会計と一致することはスタッフが確認します。アプリがレジから自動で金額を取得・検証する仕組みではありません。

QRは会員を提示するための短時間有効な情報で、有効期間は2分です。QRを見せるだけではスタンプ付与やクーポン使用は成立しません。スタッフのログイン・権限と確認操作が必要です。

会員番号での検索は、スタッフの業務操作として用意します。これは会員本人のログインや、アカウントの所有者確認を置き換えるものではありません。

## 通信・重複・操作記録

本番の業務操作にはインターネット接続が必要です。端末内でスタンプを仮加算して後から送る処理は行いません。通信できないときは、接続を確認してから操作を再試行します。

付与とクーポン発行は、共有データベースでまとめて確定します。同じ日の複数端末からの付与、連打、同じ操作の通信再送を重複処理しません。クーポン使用も、未使用・期限内の場合だけ1回成立します。処理日はサーバーの時計で判断するため、お客様のiPhoneの時計を変えても付与条件は変わりません。

スタッフによる付与・使用・お知らせ編集・権限変更には操作記録を残します。誤操作時はオーナーが記録を確認します。残高の手動変更、クーポンの使用取り消し、期限延長のルールは未指定のため、通常の店舗画面に任意変更の機能は設けません。

共有データベースの管理用ログインと、アプリの運用サーバー用ログインは分けます。DB準備後、初回設定コマンドで実行専用の`tamaya_runtime`を作成し、公開APIにはその接続情報だけを設定します。スタッフやお客様へDB接続情報を配りません。具体的な設定順は[本番版の引継ぎ・開始手順](PRODUCTION_HANDOVER.md)を参照してください。

## 退会・個人情報

お客様はアプリ内から退会を開始できます。直前のパスワード確認を行い、会員データとFirebaseのログイン情報の削除を処理します。外部の認証サービスの削除が一時的に失敗した場合は、削除処理を保留してサーバー側で再試行します。保留を「すべて削除できた」と表示しません。

スタッフ・オーナーの権限が有効なアカウントは、先に権限を停止してから退会します。自分が最後の有効なオーナーの場合は、先に別のオーナーを登録して引き継ぎます。会員データの削除と、業務上残す記録・バックアップの取り扱いは、公開するプライバシー文書と実際の保存・復旧設定を一致させます。

## 運用開始前に確定すること

スタンプ・特典の条件に関する追加回答は不要です。残る次の準備がそろった後に、実際のお客様向けの運用を開始します。

- 掲載済みの店舗情報の最終確認と、臨時休業などのお知らせ運用。
- 公開用の利用規約・プライバシー・問い合わせページの内容。実際の委託先・保存地域・保管期間も運営者が確認する。
- 実際に使うFirebase・Supabase・サーバー公開先のアカウントと接続設定。
- バックアップ、障害時の連絡、登録メールが使えない場合の本人確認方法。

設定と作業の手順は[本番版の引継ぎ・開始手順](PRODUCTION_HANDOVER.md)、実行した確認は[検証結果](VALIDATION.md)を参照してください。
