# 今の試作品から、玉屋で使う本番アプリへ改修する手順

更新日：2026年10月26日（日本時間）。この文書は、iPhoneで試作品の確認を終えたところから、実店舗で使う仕組みを作るための手順です。

**既存のiPhoneアプリは端末内デモです。管理サーバーの土台を`server`へ追加し、データベース・権限制御・付与と使用のAPI・Firebase IDトークン検証を実装しました。** [管理サーバーの起動手順](../server/README.md)で、架空データによる操作を試せます。アプリ側のFirebaseログインとAPI接続、実Firebase・iPhoneでの統合確認、公開先への配置はこれからです。外部アカウントの作成、有料契約、本番環境の変更、Appleへの申請は実行していません。

まずは**玉屋1店舗で、お客様のiPhoneと店舗の別端末が同じ会員データを使えること**を目標にします。他店舗用の画面や店舗向け課金機能は、そのあとに検討できます。データの設計には店舗を区別する項目を用意します。

以下では「利用者・店舗が決めること」と「開発担当がプログラムを作ること」を区別しています。アカウントを登録するだけでは、本番機能は追加されません。

## 1．公開形式と運用ルールを決める

担当：利用者と玉屋の運営者。

Windowsのメモ帳などに、次の表の回答を書いて保存してください。未定の項目は「未定」と記入できます。下記の試作条件を、そのまま正式条件にしたことにはしません。

| 決める項目 | 回答欄・確認内容 |
| --- | --- |
| 公開する形 | 未定：店舗ごとの専用アプリ／共通アプリ内の店舗ページなど |
| 店舗とアプリの運営者 | 未定：誰がサービスを提供し、問い合わせに対応するか |
| お客様の登録・ログイン方法 | 未定：メールの確認コードなど。ニックネームだけでは機種変更時の本人確認ができないため、復旧方法も決める |
| 店舗で使うスタッフ | 未定：利用する人、管理者、退職・端末紛失時に停止する担当 |
| 正式なスタンプ条件 | 未定：試作は来店1回・日本時間で1日1回 |
| 正式な特典条件 | 未定：試作は10個を消費して100円引き、発行から30日 |
| 割引の対象・併用条件 | 未定：実際に店頭で使える条件 |
| 掲載する店舗情報・問い合わせ先 | 未定：住所、営業時間、電話番号、メールなど |

電話番号によるSMS認証を選ぶ場合は、送信費用も確認します。メール認証やAppleでのサインインにも、それぞれ設定と開発が必要です。客層と復旧しやすさを踏まえて選びます。

ニックネームだけで始める設計も候補になりますが、別端末で復旧するにはメールやAppleアカウントなどとの紐付けが必要です。最初に本人確認を必須にするか、利用後に連携できるようにするかも決めます。

**完了の目印：登録・特典・スタッフ・公開形式について、決まった内容と未定の内容が一覧になっている。**

## 2．共有の保存先を準備する

担当：アカウントの準備は利用者、接続方法の設定は開発担当。

サーバーは、お客様と店舗が同じ会員情報を使うための仕組みです。ここでは、認証とデータベースを扱える**Supabaseを使う場合の具体例**を示します。まだ採用や契約を決定した状態ではありません。

追加した管理サーバーは、Firebase Authenticationを本人確認に使い、保存先にはSQLiteを使用しています。SQLiteは永続ディスクを持つ単一サーバー向けです。Supabaseなどの別データベースへ移す場合は、保存処理と作成用SQLの移行も行います。以下のSupabase準備は、そのサービスを採用する場合の案内です。

Supabaseを採用する場合は、まず架空の情報だけを入れる開発用環境を準備します。

1. PCのブラウザーで [Supabaseの管理画面](https://supabase.com/dashboard)を開きます。
2. 自分で管理できるアカウントを作成し、ログインします。
3. Organizationの作成・選択が求められたら、今回の開発を管理するものを用意します。料金と契約名義を確認し、無料プランで開発する範囲を選びます。
4. `New project`から新しいプロジェクトを作ります。
5. 名前には、例えば`tamaya-development`と入力します。これは開発用であると分かる管理名です。
6. データベース用パスワードを設定し、パスワード管理アプリなどへ保存します。
7. RegionでTokyoが選べる場合は候補にできます。提供地域と保存場所を確認して選びます。
8. 入力内容・料金を確認し、作成後の準備が完了するまで待ちます。
9. プロジェクトの`Connect`や、`Settings`内のAPI関連の画面から、Project URLと接続に使う公開用キーを確認します。画面の名称は変更される場合があります。

接続情報には種類があります。

| 情報 | 扱い |
| --- | --- |
| Project URL | 接続先を示す情報 |
| Publishable key／旧形式のanon key | アプリから使う公開用キー。これ自体でスタッフ権限を与えるものではない |
| Secret key／service_role key、DBパスワード | 管理用の秘密情報。アプリに埋め込まず、チャットや公開GitHubにも載せない |

キーを開発担当へ渡す場合は、種類を確認して必要なものだけを渡します。管理画面全体のスクリーンショットには秘密情報が含まれることがあります。

料金・無料枠・休止条件・バックアップ条件は、[料金画面](https://supabase.com/pricing)で確認します。無料プランでは利用状況による休止などの条件もあるため、本番の稼働・復旧条件を別途確認します。

メール認証を選ぶ場合、標準のメール送信は原則としてSupabase組織のチームメンバー宛に制限されます。**一般のお客様や任意のスタッフのメールで試す前に、開発担当が[カスタムSMTP](https://supabase.com/docs/guides/auth/auth-smtp)と送信元ドメインなどを設定します。** メール配信サービスの料金・送信制限も確認します。この設定は、2端末の登録テストより前に必要です。

**完了の目印：利用者が管理できる開発用プロジェクトがあり、接続先と公開用キーの種類を確認できている。まだ実在のお客様の情報は入れない。**

## 3．データベースの設計を作る

担当：開発担当。

現在のデータは、会員・履歴・クーポンをまとめた端末内のデータです。本番用には、少なくとも次を分けて保存します。

- 店舗と、承認されたスタンプ・特典条件。
- ログインする本人と、店舗ごとの会員登録。
- スタッフと、担当する店舗・権限。
- スタンプの付与履歴、クーポン、お知らせ。
- 誰がいつ付与・使用・編集を行ったかという操作記録。

将来の店舗追加に備え、店舗のデータには`store_id`という店舗を区別する値を持たせます。画面は玉屋1店舗に集中しながら、別店舗の情報が混ざらない構造を作れます。

クーポンには、発行時の割引額・期限・条件も保存します。現在の試作は表示時の設定値を使うため、条件変更後も過去のクーポンを正しく表示する改修が必要です。

データベースを作成・変更するファイルをソースに保存します。利用者が管理画面へ未確認のSQLを貼り付ける手順は、この段階では用意していません。

**完了の目印：必要なデータの関係と作成・変更手順が整理され、開発用環境で再現できる。**

## 4．本人確認とスタッフ権限を実装する

担当：開発担当。利用者は、必要なスタッフの登録を確認します。

お客様の登録・ログイン・ログアウト・復旧を実装します。お客様は本人の会員証、履歴、特典を扱います。スタッフは担当店舗の業務に必要な情報を扱います。

画面上で店舗メニューを隠すことに加え、サーバー側でも毎回、実行者と権限を確認します。Supabaseを採用するなら、RLSなどのデータアクセス制御も設定します。お客様が自分でスタッフ権限を付けられる構造にはしません。

ログイン状態を安全に保存する方法、ログアウト時の情報の消去、スタッフ権限を外した後のアクセス停止も実装します。店舗管理者がスタッフの利用を停止できるようにします。

**完了の目印：他のお客様の情報を読めず、お客様からの付与要求を拒否し、担当外の店舗にもアクセスできない。**

## 5．スタンプ・クーポンの処理をサーバーへ移す

担当：開発担当。

日付や期限はサーバーの時刻から日本時間で判定します。お客様のスマホの時計を変えても、付与日や有効期限が変わらない仕組みにします。

スタンプの付与では、次をひとまとまりで確定します。

1. スタッフ権限と対象会員を確認する。
2. 同じ店舗・会員・日本の日付に付与済みでないか確認する。
3. 付与履歴と残高を更新する。
4. 条件を満たした場合だけ、スタンプを消費してクーポンを1枚発行する。

クーポン使用では、未使用かつ期限内の場合だけ使用済みにします。複数の店舗端末が同時に押しても、成立する処理は1回にします。

通信が途中で切れて同じ操作を再送した場合も、重複しない仕組みを入れます。確定した操作には、担当スタッフと処理結果の記録を残します。

**完了の目印：同日・連打・複数端末・通信再試行でも重複せず、9個からの付与で残高0・クーポン1枚になる。**

## 6．アプリを本番用APIへ接続する

担当：開発担当。

現在の`DemoRepository`は、端末内の会員・履歴・特典などをまとめて読み書きしています。この全データを、そのままネット上へ保存する方法では本番化できません。

本番用には、本人・担当店舗の範囲に絞った読み取りと、サーバーが確定する操作へ分けます。例えば「自分の会員証を読む」「会員登録する」「対象会員へ付与する」「クーポンを使用する」「お知らせを編集する」というAPIです。

ホーム・会員証・特典・お店を、この接続へ切り替えます。読み込み中、未登録、通信失敗、再試行の表示も用意します。端末内に表示用データを残す場合も、正しい残高や使用状態はサーバー側で管理します。

通信結果が確認できないときは、成功と表示せず、確認中や再試行の案内を出します。

**完了の目印：お客様の端末で登録した会員が店舗の別端末に現れ、付与・使用の結果がお客様側にも反映される。**

## 7．会員QRと店舗画面を本番用にする

担当：開発担当。

現在のQRはデモ用の会員IDを含むものです。本番では、期限付きの提示用情報などを設計します。会員番号やQRを知っているだけで、付与・使用ができる仕組みにはしません。

店舗では、スタッフとしてログインしたうえでQRを読み、対象会員を確認し、付与・使用を確定します。期限切れ・無効なQRの案内や、読み取りをキャンセルする操作も用意します。

公開版から、誰でも店舗側へ入れるデモ切り替え、サンプル会員、デモ初期化を除外します。これは既存の本番データを削除する作業ではありません。開発用の見本データと本番データを分けて管理します。

**完了の目印：スタッフ認証後だけ業務操作でき、実際のカメラで読み取ってから対象を確認できる。**

## 8．復旧・退会・日々の運用を整える

担当：開発担当と利用者・店舗。

機種変更やアプリの再インストール後に会員を復旧する方法を実装します。会員アカウントを作れる場合は、アプリ内から退会・削除へ進めるようにし、サーバーに残る情報と必要な保存の扱いも決めます。

正式な店舗情報、問い合わせ先、プライバシーポリシー、利用条件を入れます。管理側では、バックアップと復元方法、障害時の担当、スタッフの追加・停止手順を決めます。

**完了の目印：復旧・削除・スタッフ停止を実際に試せて、問い合わせ先と障害時の対応方法が決まっている。**

## 9．自動テストと、2端末の操作確認を行う

担当：自動テストは開発担当、実店舗の操作確認は利用者・店舗。

現在の自動テスト27件は端末内デモの確認です。サーバーの権限と同時操作を確認するテストを追加します。

- お客様が自分にスタンプを付与できない。
- 他の会員・店舗の情報へアクセスできない。
- 日本時間の日付境界、10個の消費、30日の期限を正しく扱う。
- 2台から同時に付与・使用しても、1回しか成立しない。
- 通信が切れた後の再試行で、重複や誤った成功表示がない。
- 再ログイン、復旧、退会削除、スタッフ権限の停止が機能する。

架空の会員を使い、お客様役のiPhoneと店舗役の別端末で、登録から特典利用まで通して試します。メール認証の場合は、手順2の配信設定を済ませてから一般のメールアドレスで確認します。機種・OS・操作・結果・気づいた点を記録します。9スタンプの見本などは、開発・検証用の環境に用意します。

**完了の目印：サーバー側のテストと2端末の実機確認が完了し、残った問題が記録・修正されている。**

## 10．本番環境へ反映し、TestFlightで確認する

担当：環境と実装の準備は開発担当、名義・契約・店舗での受け入れ確認は利用者。

開発用とは分けた本番環境を用意し、正式な設定を反映します。サンプル会員や開発用スタッフを本番の会員として引き継ぐ運用にはしません。料金、バックアップ、メール配信、障害対応を本番で使う条件に合わせます。

その後、正式なアイコンやAppleの登録をそろえ、署名付きアプリを作ってTestFlightへ配布します。Expo Goでの確認とは別に、玉屋のアイコンから起動するアプリで、2端末の登録・付与・特典利用を再確認します。

具体的なビルド・提出・審査の操作は、[App Store公開手順書](APP_STORE.md)へ進んでください。

**完了の目印：本番用の接続先で、Expo Goや起動用PCなしに操作でき、店舗の別端末と正しい状態を共有できる。**

## 今の段階で最初にすること

1. 手順1の回答表を埋め、決定済みと未定を分けます。
2. Supabaseを採用する場合は、手順2で開発用プロジェクトを準備します。
3. 開発担当がデータベース・権限・API・アプリの改修を順に実装します。
4. 自動テストと2端末の検証後、本番環境、TestFlight、App Store審査へ進みます。

本番用の追加実装ができるまでは、手元の試作品を保管しておけます。現在のニックネームやスタンプのデモデータは、実店舗の正式な会員データとは別に扱います。
