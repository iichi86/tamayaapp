## 1．完了：Renderの稼働確認

11月2日、所有者の画面で`dd84795`が`Live`になったことを確認しました。続いて所有者から、`https://tamayaapp.onrender.com/health`が`status=ok`、`authMode=firebase`であるとの報告を受けました。この確認は、以後の変更まで反映済みであることを示すものではありません。

退会から90日後を待つ試験や、本番の残高・日付を変更する操作は必要ありません。

## 2．完了：確認用会員の退会とログイン拒否

別のメールアドレスで作成し、スタッフ権限を停止した0スタンプの確認用会員を対象に実施しました。11月3日までに所有者の実機画面で「退会とアカウント削除が完了しました。」を確認し、削除後に同じメールアドレス・パスワードでログインが拒否されたとの報告を受けました。オーナーとして日常管理に使う会員は、この削除の対象にしていません。

退会の確認は完了しています。確認用会員の再作成・再削除は不要です。

## 3．PC側のビルド用ファイルを更新する

ZIPで使っているWindows側へ、ビルドに渡すファイルの整理とNodeの指定を反映できます。アプリ直下の黒い画面で次を1行ずつ実行します。

```bat
cd /d "%USERPROFILE%\Downloads\tamaya-server-setup\tamayaapp-main"
```

```bat
curl.exe -fL --retry 3 "https://raw.githubusercontent.com/iichi86/tamayaapp/84c1af5afdeadc199e0bd905d1926d4b25cb6106/.easignore" -o .easignore
```

```bat
curl.exe -fL --retry 3 "https://raw.githubusercontent.com/iichi86/tamayaapp/84c1af5afdeadc199e0bd905d1926d4b25cb6106/eas.json" -o eas.json
```

取得エラーが出た場合は、その表示を確認してから続けます。この2ファイルに加えて、公開文書の正式反映後の店舗設定やアプリ設定もビルド前に更新します。EAS側のBundle ID追加は完了済みで、再登録は不要です。PCの`.env`とExpoの最終設定の一致を照合して署名準備へ進みます。

## 4．決定した掲載名と正式ロゴを反映する

11月4日、所有者が掲載名「むさしの玉屋」と、アイコンを店舗の正式ロゴへ変更する方針を選択しました。正式ロゴの画像は未受領です。原本を受け取り、アイコンへ反映します。現在の[深緑と「玉」のデザイン](../assets/app-icon.png)は仮のままです。掲載名のApple側での利用可能性は、App Store Connectへ入力する際に確認します。

App Store用の実機スクリーンショットは、署名付きアプリが完成した後に撮影します。今は撮影する画面と文章を準備する段階です。

## 5．バックアップの運用を選ぶ

手動取得の手順は準備済みです。自動取得を選ぶ場合、Supabase Proは基本月額25米ドルで、直近7日分の日次バックアップが含まれます。税・為替・追加利用分は公式の契約画面で確認します。毎日正常に取得できても、直近の取得から後の最大約1日分は含まれない可能性があります。

有料契約はまだ選択・実行していません。実際のお客様の会員運用を始める前に、取得担当、保存先、日次取得、復元手順を決めます。保管7日分は手動運用の提案で、採用済みの規則ではありません。

Supabase Proへの変更は、署名付きアプリの準備より前に行う必須作業ではありません。まず現在のFreeのまま準備を進め、実際の顧客運用の開始前にバックアップ運用を確定します。提供事業者の未確認のログ保存日数を推測で固定せず、公開文書では各社の保存・削除条件に従う扱いを示します。
